# 黑箱｜提交用一页说明

## 项目定义与目标用户

黑箱（HackKit）是面向黑客松参与者的独立微工具箱：用户可以按需打开工具，完成协作推进、投票组织、公开仓库检查和交付文档整理，不要求先组队、再开发、再提交，也不把招新面试看成产品的使用流程。社团招新面试只是展示项目能力的场景，产品本身服务的是黑客松现场的参赛者。

## 我负责的部分

我负责把需求拆成可验收的任务与边界，确定“输入 → 处理 → 结果/导出”的闭环标准，维护项目基线、接口约束和本地运行说明，并参与各工具的方案取舍、集成复核、错误态检查和最终文档交付。仓库现有实现包括统一目录、公开 GitHub 只读检查、文档生成、正式看板和投票墙等模块；这里的“负责”指对需求、协作和验收结果负责，不假定由我独立手写每一行代码。具体实现以仓库提交和可复现命令为准。

## AI 使用情况

开发过程中使用 Codex 辅助拆解任务、设计边界、编写和审查代码及文档；所有需求判断、代码修改和演示结论均由人工核对。项目内保留了仅服务端可调用的 DeepSeek adapter，但本次未配置 `DEEPSEEK_API_KEY`，未启用真实模型调用；文档助手也不会自动补造项目事实，而是依据用户输入整理并列出缺失项。因此没有伪造模型调用记录，也没有把模型输出当作未经审查的事实。

## 最大困难与解决方式

最大的困难是区分“浏览器里能演示”与“线上真的安全可用”。解决方式是把本机演示、服务端权限会话和未来正式版分层：正式工具在本机使用服务端 HttpOnly session 与权限检查；多人工具明确标注 `same-browser-demo`，不宣称账号认证、跨设备共享或公网协作。第二个困难是 GitHub API 限流、无效链接和上游故障，检查器因此分别返回 `pass/fail/unknown` 及可追溯证据和错误状态，而不是把无法确认写成失败。已验证的是本地输入、处理、结果/导出闭环及代码级错误边界；尚未验证的是公网部署、真实跨设备协作、真实 DeepSeek 调用和线上限流表现。

## 四个工具

- 正式进度看板：自选 ID/密码进入本机 session，管理活动、队伍、任务和邀请。
- 正式投票墙：在会话和活动规则约束下提交单票，按状态展示结果并防止重复投票。
- GitHub 仓库检查：输入公开仓库 URL，读取公开 API/页面并输出检查项、证据和限流等错误态。
- 项目文档助手：输入项目名称、目标和功能资料，整理 README 与一页说明，支持编辑、复制和 Markdown 下载。

## 本地运行与验证

要求 Node.js 20.9+：`npm ci` 后运行 `npm run dev`，访问 `http://localhost:3000/`。可复现验证命令为 `npm run lint`、`npx tsc --noEmit`、`npm test`、`npm run build`；验证重点是输入闭环、权限/错误提示、刷新恢复和不把路线图伪装成已完成功能。当前结论仅限本机可复现范围。
