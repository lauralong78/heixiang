# 黑箱操作与测试指南

本指南按当前本地开发站点使用。打开 `http://localhost:3000` 后，从工具目录进入任一工具。

## 先分清两种模式

| 标识 | 工具 | 数据与边界 |
| --- | --- | --- |
| **本机演示** | 组队名片、仓库检查器、进度看板、现场破冰、队友匹配、观众投票墙、签到与领取、项目文档助手 | 大多保存在当前浏览器；刷新可恢复本浏览器数据，但不代表账号、跨设备同步或真实线上授权。|
| **正式服务（开发中）** | 正式版看板、正式投票墙 | 使用自选 ID、密码与服务端 session；活动内的角色由服务端决定。没有通过完整线上验收前，不把它当作已上线服务。|

> 测试前先记住：本机演示与正式服务的数据完全分开，不能从一个模式直接看到另一个模式的活动或记录。

## 通用操作

1. **刷新数据**：本机演示按浏览器 `Ctrl + R`；正式页刷新会重新检查会话和读取可见数据。
2. **等待反馈**：看到“正在发起请求 / 正在等待服务端确认”时，先等待结果，不要连续点同一个按钮。失败时页面会说明结果是否确认。
3. **导入前备份**：凡有导入/恢复功能的本机工具，先导出 JSON；导入会替换该工具当前浏览器内的数据。
4. **测试权限**：本机演示可在页面明确切换 host / participant / viewer；正式服务必须使用不同账号或有效邀请，不能依赖前端按钮伪造身份。

## 1. 组队名片 `/tools/card`

1. 填写昵称、角色、技能、兴趣和简介。
2. 确认右侧预览实时变化。
3. 点击下载 PNG，检查导出的图片内容与预览一致。
4. 刷新页面，检查草稿是否仍在当前浏览器恢复。

测试重点：空字段、长文本、特殊字符、PNG 是否真的下载而不是只有提示。

## 2. 仓库检查器 `/tools/repo-check`

1. 输入公开 GitHub 仓库地址，格式必须是 `https://github.com/owner/repo`。
2. 点击开始检查，等待“已确认 / 缺失 / 无法确认”的证据结果。
3. 分别测试有效公开仓库、错误地址、私有仓库或受限仓库。

测试重点：限流或网络失败必须显示 `unknown`/无法确认，不能把失败说成仓库缺项。此工具不读取私有仓库，也不需要 GitHub Token。

## 3. 本机进度看板 `/tools/progress-board`

1. 创建本地活动并设置截止时间。
2. 新增至少两支队伍和若干任务，修改任务状态、进度和负责人信息。
3. 检查总进度和倒计时是否跟随变化。
4. 导出 JSON；刷新页面；再导入导出的 JSON，确认记录恢复。

测试重点：非法 JSON、错误工具备份、超限文件不得部分覆盖现有数据。

## 4. 现场破冰 `/tools/icebreaker`

1. 填入参与者昵称、技能、兴趣及排除关系。
2. 生成第一轮配对，再生成下一轮。
3. 检查奇数人数是否轮空、重复组合是否尽量减少、理由是否只使用填写的信息。

测试重点：排除关系不可被配到一起；没有足够资料时必须说明证据不足，而不是编造理由。

## 5. 队友匹配（本机演示）`/tools/team-match`

1. host 创建活动；加入两位 participant 和可选 viewer。
2. 分别填写 `public / limited / private` 资料，确认 private 资料不会出现在推荐中。
3. 在参与者身份发起邀请；在接收方身份接受或拒绝；再测试撤回和退出。
4. 导出、刷新、导入，检查邀请与匹配历史恢复。

测试重点：这是**同一浏览器演示**，不是注册账号或跨设备匹配；viewer 不可写入，参与者不能代替别人处理邀请。

## 6. 观众投票墙（本机演示）`/tools/vote-wall`

1. host 创建活动、候选作品，设置 `hidden / live / final` 结果规则及投票资格。
2. 切换到 participant，投一票；再次投票应得到“已投”而不是增加票数。
3. 切换到 viewer，确认没有投票入口。
4. host 在关闭前带原因 void 一票；关闭活动后再试图修改。
5. 导出结果和 JSON 备份，确认“本机演示”标识存在。

测试重点：不要把身份切换当成真实账号，也不要测试为跨设备投票。

## 7. 签到与领取（本机演示）`/tools/checkin-claim`

1. host 创建 `check-in`、`claim` 或组合活动，建立名单并发放本地凭证。
2. 用 participant 身份或凭证完成签到/领取。
3. 重复同一动作，确认返回原记录而不是新建第二条。
4. 测试未知凭证、错误活动凭证、已退出成员；再导出 CSV。

测试重点：签到与领取是两类独立记录；原始凭证不应出现在 CSV、日志或错误信息中。

## 8. 项目文档助手 `/tools/docs-assistant`

1. 输入已经确认的项目事实：目标、用户、功能、技术栈、运行方式等。
2. 生成 README 和一页说明，检查“缺失信息”是否单独列出。
3. 编辑结果后复制或下载 Markdown。

测试重点：它只能整理输入的事实；不要把它生成的内容当成已验证的部署、奖项或功能证明。

## 9. 正式版看板 `/tools/formal-board`

1. 用自选 ID 和密码注册；注册完成后按页面提示切到登录。
2. 登录成功后创建活动，或粘贴收到的邀请加入活动。
3. host 生成活动/队伍邀请；队长创建队伍任务、分配成员；成员更新自己被分配的任务进度。
4. 使用“刷新数据”等待服务端同步；遇到冲突或失败，按页面提示刷新后再操作。
5. 可选填写联系方式；它只对本人可见。附件区域目前只做元数据校验，不把“已准备”理解成文件已经上传到外部对象存储。

测试重点：不同账号看到的权限必须不同；不要在同一账号中试图把 collaborator 改为 host。正式功能仍需真实双浏览器、迁移、附件与权限的完整验收后才能称为可上线。

## 10. 正式投票墙 `/tools/formal-vote-wall`

### Host 创建并开启投票

1. 使用活动 host 账号登录，并在右上角身份卡确认显示“主持人”。
2. 选择活动；左侧出现 **创建一张正式投票**。
3. 填写标题、结果规则后点 **创建 draft**。
4. 添加候选项；确认 draft 设置后，点 **开放投票**。
5. 关闭投票会冻结投票与结果，操作前需确认。

### 成员参与投票

1. 使用已加入活动的协作者账号登录；右上角身份卡会显示“协作者”。
2. 选择活动，并使用 host 创建后提供的投票链接或投票 ID 打开对应投票。
3. 在开放状态选择一个候选项投票。每个合资格成员只能有一票。

当前已知体验限制：活动列表 API 尚未自动返回投票 ID，因此 host 仍需要把创建后的投票链接/ID提供给成员；不要把活动 ID 当作投票 ID。

## Bug 反馈格式

请每个问题单独发送以下信息，赤玉会先复现再修：

```text
工具和地址：例如 正式投票墙 /tools/formal-vote-wall
当前身份：例如 host / collaborator / participant / viewer
操作步骤：1. … 2. … 3. …
预期结果：…
实际结果：…
是否刷新后仍存在：是 / 否
截图或错误文字：…
```

不要发送密码、Cookie、Token、原始签到凭证或任何 Secret。截图中若含邀请码、投票 ID、联系方式或私人附件名，先打码再发送。
